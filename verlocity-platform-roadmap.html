Sprint 6 Sep 10, 2026
Opportunity View rebrand + a real data-integrity fix, platform-wide
Shipped
  • Renamed Command Center → Opportunity View across the product (title, header, index tile, cross-references); renamed 3 files to match their real names (opportunity-view.html, intelligence-hub.html, growth-map.html) with redirect stubs left at the old paths so nothing already shared breaks. Removed the unused, unreferenced bmap_hub_lite.html.
  • Opportunity View polish: fixed a unit bug ($4940M → $4.94B), rebuilt the Radius Market Summary panel from a horizontal-scroll table to a stacked layout, wired the 3 What's Next cards to select the branch on the map (matching a marker click exactly) and added Zone/Play to both that card and the map-selected card, defaulted the app to 85% zoom density.
  • Rate Radar in Opportunity View: reversed last night's "hide unverified" filter back to showing all data with a quiet confidence marker instead of a loud warning — for internal product review, not a customer meeting, where the fully-hidden version made well-populated banks look empty.
  • Platform-wide fix, part 1: rebuilt analytics.branch_target_competitors (top-3 named competitors per branch — feeds Rate Radar, every capture-potential table, ROI math, and the real assessment docs, for all 9,162 institutions) using adaptive-radius + precise-distance logic ported from bmap_branch_preview.py's determine_adaptive_radius(), replacing a flat 10-mile search against a stale, quantized-distance table. Backed up first (branch_target_competitors_backup_20260910, _old_20260910 both still live), validated against 3 real institutions before the real swap, built as 32 batched inserts after a single-statement attempt timed out. Also updated the source refresh_bmap_scores() procedure itself, so a future call doesn't silently revert to the old logic.
  • Platform-wide fix, part 2 — the scoring engine itself: traced the same class of bug into opportunity_score's inverse-density term and found it used a flat 10-mile radius for every branch regardless of market type. Built a 3-tier adaptive classifier (analytics.determine_density_radius: 1mi dense city / 3mi suburban / 10mi rural), validated it against real dense/suburban/rural branches (Manhattan, Cincinnati suburb, rural Kansas — each showed a real 4–7x distortion, in different directions depending on market type), built full-platform precomputed tables (geo.branch_competitors_tiered_v1, branch_radius_stats_tiered_v1, 3.97M pairs, 93,604/93,604 branches covered), simulated the full-platform score/zone impact before touching anything live, sanity-checked it by name against Trustmark, Hancock Whitney, Cattlemens, Clinton Savings, and Carver — then backed up branch_opportunity_base and branch_opportunity_minmax and updated refresh_branch_opportunity_base() in place (the function every scheduled refresh already calls, so the fix is now permanent, not a one-time patch). Verified end-to-end through the real anon-key path the app actually uses (public.vw_branch_opportunity_cbsa), not just owner-level SQL.
  • Platform-wide fix, part 3 — the 16-play matrix itself: chasing "why do so few branches ever show as a priority play on the map" led to the real root cause — campaign had never implemented the authoritative 16-play matrix (Zone × Quadrant, from BMAP_Methodology_Part1.docx) at all. It used a parallel, invented scheme (Capitalize, Turnaround, Stabilize, Loyalty/Retention, Hold and Watch, No Action Needed — none of which exist in the real methodology). Confirmed the frontend (opportunity-view.html, growth-map.html, intelligence-hub.html) had the correct authoritative play names in all three of its priority-tier whitelists the whole time — they were simply never once matched by the database. Rewrote Step 9 of refresh_branch_opportunity_base() cell-by-cell against the confirmed matrix, backed up the old campaign values first (branch_campaign_backup_20260910), re-ran, and verified all 16 zone×quadrant cells now match exactly across all 93,604 branches. Also removed a dead variable in bmap_snapshot.py that referenced the old wrong names and was never actually read downstream.
  • Fixed Rate Radar's "Named competitors" panel showing only 3 institutions for Hancock Whitney instead of its real 126 — loadRateRadar() fetched with limit=10 on raw branch-competitor rows, before deduping by institution name. One recurring high-vulnerability competitor (Hibernia Bank, legitimately dangerous across 8 of Hancock Whitney's branches) filled most of that limit before any other real competitor got a chance to surface. Fetch limit raised to 1,000 (matching the pattern already used in intelligence-hub.html), cap to the top 10 moved to after the dedupe. Verified by replicating the exact fetch-and-dedupe logic against the real anon-key data — 10 distinct institutions now surface, confirmed live in the browser.
  • Simplified Opportunity View's no-?bank= flow (the bare link, for internal staff use) — removed the "Select institution →" button and its separate internal-code gate, so it goes straight from the main access gate to the institution search bar. Removed the now-dead picker HTML/CSS/JS entirely rather than leaving it unreachable.
Found
  • The old competitor-selection logic had a real, live error: Addison Branch (Cattlemens Bank) had "Texas Regional Bank" as its #1 named competitor — a branch 3.4 miles away, outside the branch's own correctly-computed 1-mile radius (its market is 6x the bank's entire balance sheet within 1 mile, the exact bank-scale-override case named in the original Python docstring). Not an isolated case — the same stale geo.branch_competitors_10mi_v2 table fed both this and the radius panel bug fixed earlier tonight.
  • Credit unions (cu_XXXXX inst_keys) broke the bank-id derivation the reference Python logic uses (it skips CUs entirely) — fixed more completely by pulling bank_id straight from geo.branches_master_v2 instead of parsing inst_key text.
  • A single-statement full-platform rebuild hits a real timeout — needed batching (300 institutions/batch, ~32 batches) the same way branches_within_radius_batch already had to for the same underlying reason.
  • A bigger, separate bug: 22,049 branches — 23.6% of the entire platform — had zero rows in the old geo.branch_radius_stats_10mi_v2 table, not "no competitors found" but never covered by that stale snapshot at all. The scoring formula's COALESCE(...,0) silently zeroed their density term (25% of the score) this whole time. Confirmed with a real example: Hancock Whitney's Niceville, FL branch sat at score 19.85 ("Justify") despite 100% YoY growth against shrinking peers — corrected to 71.49 ("Invest") once it had real data to score against.
  • Even branches whose radius didn't change (rural, still 10mi) shifted, because the new competitor set is freshly computed and precise, not a stale/quantized snapshot — confirmed via Trustmark's Taylorsville Branch, where the old table counted a "competitor" that doesn't exist under precise distance.
  • Sanity-checked against 6 real, named banks before shipping: Hancock Whitney and Trustmark's previously-flagged rural branches (Pinhook, Y Branch) both lost ground as expected; Clinton Savings' four branches — previously bunched within 1 point of each other — now spread across an 11-point range; Carver Federal's Harlem HQ branch (dense, 1mi tier) jumped from Defend to Invest, the same dilution pattern proven on the Manhattan BofA example.
  • Investigated whether the $10B community-bank baseline used for zone thresholds was too strict for our actual "community + regional" customer definition (proposed raising it to $50B). Real data said no: smaller banks already get proportionally more Invest-zone labels than anyone (30.0% for sub-$1B, decreasing steadily to ~25% for $50B+ megabanks) — raising the baseline tested net-negative (1,072 downgrades vs. 583 upgrades) and was correctly not shipped. The real "too pessimistic" cause turned out to be the 16-play matrix bug above.
  • Found a genuinely separate data-quality issue while investigating: 18,183 branches (institutions with no row in bank_financial_snapshot_latest) score meaningfully worse than every real size bucket, including megabanks (18.5% Invest vs. 30.5% Justify) — almost certainly a data-linkage gap, not a performance signal. Not investigated further tonight.
Open questions
  • public.network_top_targets is built FROM branch_target_competitors via populate_network_top_targets() — not re-run tonight, so it still reflects the old data until someone refreshes it.
  • The updated refresh_bmap_scores() procedure's Step 2 is still one un-batched statement — if anyone calls it directly for a full platform run, it'll likely hit the same timeout that required batching tonight. Needs a real batched-procedure rewrite, not just corrected logic, before it's safe to invoke as-is.
  • The new geo.branch_competitors_tiered_v1 / branch_radius_stats_tiered_v1 tables are a snapshot, same as the ones they replaced — they'll drift stale the same way unless someone schedules a periodic rebuild. Not solved tonight.
  • analytics.branch_opportunity_base has RLS enabled with zero policies defined — found while verifying via the anon-key path, pre-existing and not caused by tonight's work (the app reads through public.vw_branch_opportunity_cbsa instead, which works correctly), but may be the same category as Sprint 1's "RLS gap on 3 BMAP_v1 tables."
  • The 18,183-branch missing-financial-data cohort found tonight — worth its own investigation into why the link to bank_financial_snapshot_latest is missing for that many institutions.
  • 5 backup/old tables now sitting in Supabase from tonight's three fixes (branch_target_competitors_backup/old_20260910, branch_opportunity_base_backup_20260910, branch_opportunity_minmax_backup_20260910, branch_campaign_backup_20260910) — drop later once confidence builds, or keep indefinitely?
  • Removing the bare-link internal-code gate means the main access code is now the only thing standing between that link and a searchable list of every institution on the platform. Was a deliberate double-gate before tonight ("so a client who only has the main passkey can never reach a searchable list") — worth confirming that tradeoff is intended now that the link is being shared with the team.
